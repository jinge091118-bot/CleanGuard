## 0. 评估前提

R10 是 V0.2 的**最后一个门禁**。它的决策对象是「是否立项 V0.3」，而不是「V0.3 做什么」。

**重要前提**：R10 的评估必须基于 R9 的实际结果。R9（V0.2 正式发布）尚未完成 —— 目前的状态是：

| 门禁 | 状态 | 说明 |
|---|---|---|
| R0 代码冻结 | ✅ | — |
| R1 正式签名 | ✅ | 受保护的 upload key 已配置 |
| R2 设备矩阵 | ⬜ | 已通过 7 个平台，但缺 vivo/Honor/Samsung/物理 Pixel 四家 OEM + 手测场景 |
| R3 物理性能 | ⬜ | harness 就绪，真实性能数据待真机 |
| R4 合规材料 | ✅ 草案完成 | 待项目所有者批准 + 隐私政策公开 URL |
| R5 内部测试 | ⬜ | 未开始 |
| R6 封闭测试 | ⬜ | 未开始 |
| R7 反馈评审 | ⬜ | 未开始 |
| R8 缺陷清零 | ⬜ | 未开始 |
| R9 正式发布 | ⬜ | 未开始 |

**结论先行**：R10 的正式决策在 R9 之后。现在能做的是**预评估**，为立项与否准备依据，而不是代替 R10 做决定。

## 1. 五个候选方向的评估

### 1.1 受保护的 Release 签名与 CI/CD 发布流程

| 维度 | 评估 |
|---|---|
| **价值** | 高。当前签名配置在本机 `key.properties`，属单机流程。CI/CD 可让构建、签名、发布可重复、可审计，降低「换台电脑发不了版」的风险 |
| **成本** | 中。需要 CI 环境、密钥托管方案（GitHub Actions Secrets / Cloud KMS 等）、产物归档、版本号管理 |
| **风险** | 中。密钥托管配置错误会导致签名不一致、无法覆盖安装已发布版本。**必须先在本地验证完整流程再迁移** |
| **前置依赖** | R9 完成并有实际发布版本（否则没有真实产物可验证流程） |
| **建议** | **立项，但排在最后一位。** 价值明确但不紧急 —— 手工发布已能完成 R9 |

### 1.2 Android 10–16 与主要 OEM 设备云回归矩阵

| 维度 | 评估 |
|---|---|
| **价值** | 高。R2 目前卡在四家 OEM 缺失上。云真机服务（Firebase Test Lab、BrowserStack 等）可覆盖这些机型，直接解决 R2 门禁 |
| **成本** | 中。主要是费用（按设备分钟计费）与 CI 集成工作 |
| **风险** | 低。纯测试基础设施，不触碰生产代码 |
| **前置依赖** | 无。**这是唯一一个能立即缓解当前 R2 阻塞的方向** |
| **建议** | **建议优先立项。** 它的价值不在 V0.3 功能，而在解决 R2/R3 的设备覆盖问题 —— 严格说更应该被视为 R2 的补充手段 |

### 1.3 Baseline Profile、Macrobenchmark 与 Perfetto 性能门禁

| 维度 | 评估 |
|---|---|
| **价值** | 高。当前 `app/build/outputs/apk/benchmark/baselineProfiles/` 为空目录 —— baseline profile 未实际生成，APK 内不含 `.prof` 文件。安装时靠 ProfileInstaller 从云端拉取，在离线或无 Play 服务设备上失效 |
| **成本** | 中。需要新建 `baselineprofile` 模块、跑一次 profile 采集、配置 CI 门禁阈值 |
| **风险** | 低。纯构建与测试配置 |
| **前置依赖** | 需要一台真机采集 profile；性能阈值需先有 R3 的物理基线数据才能定 |
| **建议** | **建议立项，且可立即开始模块搭建。** 但阈值设定必须等 R3 真实基线 —— 用模拟器或虚拟设备数据定阈值毫无意义 |

### 1.4 相似图片能力

| 维度 | 评估 |
|---|---|
| **价值** | 中。功能上有吸引力，但 CleanGuard 已有精确重复检测，覆盖了一部分需求 |
| **成本** | **高。** 需要感知哈希（pHash/dHash）或特征向量匹配，意味着要读取并解码图像内容 |
| **风险** | **高，且是隐私性质的风险。** 画面内容处理会把「只读索引」升级为「读取媒体内容」，直接改变隐私政策、Data Safety 声明、权限声明的实质内容。误判率也需要大量真机数据验证 |
| **前置依赖** | 需先修订 R4 的全套合规文档；需明确误判边界（相似到什么程度算重复？误判了用户会不会误删？）；性能开销需重新评估 |
| **建议** | **暂不立项。** 这是唯一会实质性削弱产品隐私定位的方向。README 已写明「在明确隐私、性能和误判边界后评估」—— 那些边界尚未划定。若将来要做，必须作为独立立项，不夹带在常规版本中 |

### 1.5 更完整的备份、导出或可移植设置方案

| 维度 | 评估 |
|---|---|
| **价值** | 低。当前设置项很少（大文件阈值、扫描历史保留、忽略规则），跨设备迁移的实际收益有限 |
| **成本** | 低。但与 `allowBackup="false"` 的现有决策存在张力 —— 引入备份会改变「数据不参与云备份」的隐私声明 |
| **风险** | 中。涉及隐私声明修订 |
| **前置依赖** | 需先有用户反馈证明这是真实痛点 |
| **建议** | **不立项。** 收益不匹配成本，且会削弱现有的隐私声明强度。等 R5–R7 收集到实际反馈后再评估 |

## 3. 一个需要正视的观察

从 V0.1 到 V0.2，项目的工程投入主要在**功能完备性**上：170 个源文件、约 12,400 行生产代码、39 个测试文件、Room 持久化、增量扫描、双引擎分离、重复确认、历史与恢复、12 个功能页面。

V0.2 的功能面已经相当完整。**继续叠加功能的边际收益在下降，而发布链条上的短板在凸显**：

| 短板 | 表现 | 影响 |
|---|---|---|
| 设备覆盖 | 四家 OEM 未验证 | R2 门禁无法关闭，直接阻塞发布 |
| 性能基线 | 无任何物理设备数据 | R3 无法关闭；无阈值可设 |
| 合规材料 | 需公开托管隐私政策 | R4 的最后一步依赖外部资源 |
| 发布流程 | 手工、单机 | 每次发布都是单点操作 |

**因此 V0.3 若立项，其重心更可能在工程基础设施而非新功能。** 这与 V0.2 相比是一次重心转移，需要项目所有者明确认可。

## 4. 关于 R10 决策时机的建议

R10 有两种可能的处理方式：

### 方式 A：在 R9 之后正式决策（推荐）

- R9 完成后，用真实的发布数据（用户反馈、崩溃率、留存）作为 V0.3 的输入
- 决策依据充分
- 代价：V0.3 启动时间晚

**推荐理由**：V0.3 的方向应该由 V0.2 的实际市场表现来决定，而不是在发布前凭推测决定。特别是「相似图片」这类高风险方向，是否值得做取决于用户是否真的需要它。

### 方式 B：在 R9 之前预先立项基础设施部分

- 把 §2 中「云真机矩阵」与「Baseline Profile 门禁」两项从 R10 中拆出，作为**基础设施工作**立即开始
- 这两项同时服务于 R2/R3 门禁，本身就是 R2/R3 的一部分，不算 V0.3 功能
- 纯功能性的 V0.3 立项仍在 R9 之后决策

**推荐理由**：R2 与 R3 当前的阻塞是真实存在的，等待 R9 全部完成再处理设备覆盖，顺序上是倒置的 —— R2/R3 本来就是 R9 的前置。

## 5. 建议

**立即可做（不需要新立项，属 R2/R3 范畴）**

1. 采购或接入云真机服务，补齐 vivo/iQOO、Honor/MagicOS、Samsung/One UI、物理 Pixel 四家
2. 建立 `baselineprofile` 模块并采集生成 baseline profile
3. 拿到至少一台中端真机与一台旗舰真机，按 `R3-PERFORMANCE-TEST-PLAN.md` 采集 10k/50k/100k 三档数据
4. 按 `MANUAL-SCENARIO-SCRIPTS.md` 执行手测场景
5. 完成 R4 的项目所有者审批与隐私政策公开托管

**R9 之后决策**

- V0.3 是否立项，以及重心放在基础设施还是新功能
- 相似图片能力是否在划定隐私与误判边界后启动
- 备份/导出是否值得做
