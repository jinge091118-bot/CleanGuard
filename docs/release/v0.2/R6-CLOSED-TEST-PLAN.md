# CleanGuard V0.2 R6 封闭测试方案

**状态**：草案，待项目所有者批准后执行
**前置条件**：R5 退出条件全部满足
**目标**：在接近真实的用户群体中验证稳定性与政策合规性，为 R9 正式发布积累证据

---

## 1. 轨道选择

| 轨道 | 适用判断 |
|---|---|
| **封闭测试（Closed testing）** | Google Play 对新个人开发者账号的既有要求；若账号已满足封闭测试门槛，此为推荐轨道 |
| **开放测试（Open testing）** | 仅在封闭测试已充分覆盖、且希望扩大受众时使用 |

**默认选择封闭测试。** 封闭测试允许设置测试者群组与准入条件，便于控制设备构成与收集质量更高的反馈。

---

## 2. 准入与测试者构成

### 准入条件

在 Play Console 封闭测试配置中设置：

| 条件 | 设置 | 理由 |
|---|---|---|
| 邮箱域名 | 允许公开申请 | 需要外部真实用户 |
| 国家/地区 | 优先选择已有渠道覆盖的市场 | 便于收集本地语言反馈 |
| 设备数量 | 不做硬性限制 | 覆盖面优先 |

### 目标构成

| 维度 | 目标 | 说明 |
|---|---|---|
| 测试者规模 | 建议 ≥ 20 人正式用户 | Google 对正式发布前的测试规模有实际要求，以 Console 显示为准 |
| 品牌覆盖 | 覆盖 `DEVICE-MATRIX.md` 中所有未通过行 | 内部测试未覆盖的家族在封闭测试阶段补齐 |
| Android 版本 | 10 – 16 全覆盖 | 与 R2 门禁要求一致 |
| 使用强度 | 包含至少 5 名有 500+ 媒体文件的用户 | 大数据集下的真实表现 |

**关键**：内部测试的测试者通常更愿意配合反馈；封闭测试阶段要验证的是**普通用户在没有指导的情况下**能否自己走完流程。因此要观察首次使用的困惑点。

---

## 3. 关键观测项

封闭测试阶段关注「可发布性」而非「功能完整性」（后者已由 R5 覆盖）。

| 类别 | 观测项 | 判据 |
|---|---|---|
| **首次使用** | 用户能否独立完成首次扫描 | 不提供指导的情况下，多数测试者能在 2 分钟内完成 |
| **权限认知** | 用户是否理解部分授权、回收站等概念 | 反馈中不出现「我不知道它会删除文件」类误解 |
| **误解风险** | 是否有人以为应用能清理其他应用缓存 | 若出现，需加强界面表述 |
| **性能感知** | 大数据集设备上的等待是否被投诉 | 无「太卡」「等太久」类反馈 |
| **崩溃** | 真实网络环境下的稳定性 | 崩溃率显著低于 1% |
| **耗电** | 后台耗电是否被投诉 | 无异常唤醒 |
| **政策** | Play 审核或用户提出的隐私质疑 | 零争议 |

### 特别关注：误解导致的负面反馈

CleanGuard 的核心风险是用户误解其行为。需主动监测：

- 「我把文件删了怎么找不回来」→ 检查回收站说明是否充分
- 「它怎么知道我的文件是什么」→ 检查扫描说明是否清楚
- 「为什么它要我相册权限」→ 检查权限理由文案是否到位
- 「相似照片呢」→ 检查是否已明确说明只做完全相同判定

**若某类误解反复出现，属 P2 问题**，需要通过文案改进解决，不得归为「用户理解错误」了事。

## 4. 发布节奏

| 阶段 | 时长 | 范围 | 目的 |
|---|---|---|---|
| 封闭测试第一轮 | 14 天 | 全部测试者 | 覆盖核心路径 |
| 封闭测试第二轮 | 14 天 | 全部测试者（含版本更新） | 验证修复后的版本 |
| 正式发布前终验 | 7 天 | 全部测试者 | 发布候选版本的最终确认 |

**版本更新策略**：每一轮修复后上传新 version code 的 AAB，手动推进到测试轨道。不要自动推送。

**分阶段发布**：正式发布时使用 10% → 50% → 100% 的分阶段策略，每阶段观察 ≥ 48 小时。保留随时暂停（halt staged rollout）的能力。

---

## 5. 回滚预案

| 触发条件 | 动作 |
|---|---|
| 出现任一 P0 | 立即停止分阶段发布，暂停轨道推进 |
| 崩溃率 > 1% | 暂停发布，定位后再决策 |
| 出现隐私相关质疑 | 暂停发布，先回应并确认实际行为 |
| 审核被拒 | 按 `REVIEWER-NOTES.md` 与合规文档修正后重新提交 |

**回滚不是卸载。** Play 的分阶段发布支持将新版本比例调回 0，用户侧仍可更新到上一版本。

---

## 6. 退出条件

R6 满足以下全部条件后方可进入 R7 / R8：

- [ ] 封闭测试累计运行 ≥ 28 天
- [ ] 测试者规模与设备构成达到 §2 目标
- [ ] `DEVICE-MATRIX.md` 中所有 Android 10 – 16 版本行与全部 P0/P1 OEM 家族行已通过
- [ ] P0 = 0，P1 = 0
- [ ] 误解类反馈已全部处理
- [ ] 崩溃率与耗电指标无异常
- [ ] Play Console 中无未处理的政策警告
- [ ] 项目所有者书面确认进入 R7

---

## 7. 与 R2/R3 门禁的关系

R6 的测试者反馈**不能替代** R2 与 R3 的门禁要求：

- **R2** 要求的是受控环境下的设备矩阵验证（厂商、ROM、API 级别的系统化覆盖），需要按 `MANUAL-SCENARIO-SCRIPTS.md` 执行并记录。封闭测试的散点反馈无法证明矩阵完整性。
- **R3** 要求的是带 Perfetto trace 与明确设备档位标注的性能基线。封闭测试不产生这类数据。

R2 与 R3 的门禁状态只能通过 `DEVICE-MATRIX.md` 与 `PERFORMANCE-REPORT.md` 中有证据支撑的行来关闭。
