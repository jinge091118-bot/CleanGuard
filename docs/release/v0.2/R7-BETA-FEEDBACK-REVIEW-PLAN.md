# CleanGuard V0.2 R7 测试反馈评审方案

**状态**：方案就绪，待 R6 产出反馈后执行
**前置条件**：R6 封闭测试已运行满 14 天窗口，且反馈渠道已开启
**目标**：把测试反馈转成可执行的结论，而不是一堆待办

---

## 1. 为什么要单独设一道评审

封闭测试期的反馈有两个常见的失败处理方式，两个都会把 R7 变成形式：

- 把每条反馈都当成缺陷 → 排期被淹没，真正阻塞发布的问题反而排不上
- 把反馈当成噪音 → 漏掉那些「用户根本不知道怎么用」的问题

R7 的产出是一份**评审结论**，不是缺陷列表。

## 2. 反馈来源

| 来源 | 收集方式 | 注意事项 |
|---|---|---|
| Play Console 评论与评分 | 控制台导出 | 评分低的评论优先看，附言通常更有信息量 |
| 应用内反馈邮箱 | `jinge091118@gmail.com` | 用户主动发来的多是使用障碍 |
| 测试者群组讨论 | 封闭测试群组 | 需要提前约定如何收集 |
| 崩溃与 ANR 报告 | Play Console 稳定性页面 | 按版本分组，不按单个报告看 |
| 项目自测补充 | `tools/manual-tests/run-scenarios.py` | 与测试者反馈交叉验证 |

**不收集的内容**：测试者的媒体库、文件名、相册内容。反馈里若包含这些，一律不转录到本项目文档。

## 3. 分类方法

每条反馈先归类，再决定处理方式。分类在**评审会上完成**，不由单条反馈自己决定。

| 类别 | 判断依据 | 处理 |
|---|---|---|
| **阻塞发布** | 功能不可用、数据丢失、隐私泄露、崩溃阻断主流程 | 进 R8 修复 |
| **功能缺陷** | 有明确错误结果，但有绕行方式 | 进 R8，按严重度排期 |
| **误解导致** | 用户以为会删文件、以为会上传、以为会自动清理 | 改进文案或引导，**不改行为** |
| **功能请求** | 用户想要的新能力 | 记录到 V0.3 候选，R7 不排期 |
| **环境问题** | 其他 ROM、其他 Android 版本、厂商限制 | 记录到 R2 设备矩阵 |
| **与本应用无关** | 误装、广告、其他应用 | 不处理 |

**「误解导致」这一类最容易被误判成缺陷。** CleanGuard 的核心承诺是「只处理你确认的内容」，
用户若期望它自动清理，这是产品预期与用户预期不一致，而不是程序错误 —— 改行为会直接违反
`SAFETY-RULE` 铁律。处理方式是让用户看清发生了什么。

## 4. 评审流程

### 4.1 准备（1 天）

1. 从各渠道导出反馈，去重后归入表格
2. 按类别粗分，并记录**原文**（不改写、不概括）
3. 统计各类别占比，识别集中问题

### 4.2 评审（半天）

逐条过分类表，重点确认三件事：

- 有没有**被归错类**的反馈
- 有没有反馈指向**承诺与实际不符**的地方（例如隐私声明与实际行为）
- 反馈里有没有**本应避免的场景**（说明引导不足）

### 4.3 产出（当天）

写出一份结论，包含：

| 项 | 内容 |
|---|---|
| 总量 | 各渠道反馈条数、去重后条数 |
| 分布 | 六类各自的数量与占比 |
| 阻塞项 | 每一条的复现步骤、影响面、判定依据 |
| 误解项 | 每一条的用户预期与实际行为对照 |
| 环境项 | 涉及哪些设备与 ROM，是否进 R2 矩阵 |
| 决策 | 哪些进 R8，哪些进 V0.3，哪些不改 |

---

## 5. 与其他门禁的关系

- **R8** 的输入是本评审的「阻塞项」与「功能缺陷」两栏
- **R2** 接收「环境项」；若反馈暴露出某个 ROM 上的真实兼容问题，R2 门禁状态需相应更新
- **R9** 需要本评审已签字确认，且「阻塞项」为空
