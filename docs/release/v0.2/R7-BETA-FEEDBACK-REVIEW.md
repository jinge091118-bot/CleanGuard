# CleanGuard V0.2 R7 Beta 反馈评审流程

**状态**：草案，待项目所有者批准
**前置条件**：R6 退出条件满足，反馈已通过 R5 / R6 收集
**目标**：把散点反馈转化为有结论的判断，明确哪些问题要修、哪些不改、哪些进 V0.3

---

## 1. 反馈处理原则

R7 不是「把所有反馈都修一遍」的阶段。V0.2 已代码冻结，R7 的产出是**判断**，不是代码。

| 反馈类型 | 处理方式 |
|---|---|
| P0（数据丢失、错误删除、权限绕过等） | 立即走 R8 修复流程，阻塞发布 |
| P1（核心功能不可用） | 走 R8 修复流程 |
| P2（OEM 兼容、明显性能回退、严重 UI 错误） | 评估修复成本与风险；不修需记录理由 |
| P3（轻微 UI、文案） | 评估；通常不修 V0.2，转入 V0.3 候选 |
| UX 建议 | 记录并判断是否影响核心流程；不影响则转 V0.3 |
| 性能反馈 | 与 R3 数据交叉验证；主观感受单独记录 |
| POLICY / 隐私质疑 | **优先处理**，逐条核实实际行为后回复 |
| FEATURE-REQUEST | **一律不实施于 V0.2**，进入 V0.3 候选清单 |

---

## 2. 评审会议输入

在评审开始前，每条反馈必须完成如下处理：

| 字段 | 要求 |
|---|---|
| 复现可行性 | 在什么设备/系统/步骤下能复现 |
| 影响面 | 影响多少用户、是否阻塞核心流程 |
| 与设计的冲突 | 是否与 CleanGuard 的「可解释 + 最小权限 + 用户确认」原则冲突 |
| 修复风险 | 修改是否触及安全规则、清理资格判定、权限申请逻辑 |

**不接受的输入**：无法复现且无明确证据的「感觉不对」类反馈。此类记录但不进入修复决策。

---

## 3. 决策矩阵

| 情况 | 决策 |
|---|---|
| 反馈属实 + 属 P0/P1 | 进入 R8，阻塞发布 |
| 反馈属实 + 属 P2/P3 + 改动不触及冻结区域 | 记录理由，转 V0.3 |
| 反馈属实 + 属 P2/P3 + 改动触及冻结区域 | 记录理由，转 V0.3，不在 V0.2 修 |
| 反馈属实 + 属 UX 且明显影响核心流程 | 评估文案级修复（不改逻辑），在 R8 窗口内处理 |
| 反馈不属实 | 回复说明，关闭 |
| 无法复现 | 标记「未复现」，不关闭也不修复 |
| 与产品原则冲突 | **拒绝并说明理由**，例如「要求一键清理」「要求读取全部应用列表」 |

**原则冲突的典型情形**：

| 反馈 | 回应 |
|---|---|
| 「能不能加个一键清理全部」 | 不做。全局清理会绕过用户的逐项确认，与产品原则直接冲突 |
| 「能不能读相册识别相似照片」 | 不在 V0.2 做。相似图片识别会引入画面内容处理，需先明确隐私与性能边界 |
| 「为什么不能直接删掉，还要我确认」 | 这是设计意图。移入系统回收站 + 双重确认是可逆性的保证 |
| 「能不能清理其他应用的缓存」 | 不做。Android 不提供此能力，且本应用不访问其他应用私有目录 |
| 「能不能加广告」 | 不做。无广告 SDK 是隐私声明的一部分 |

---

## 4. 隐私与政策类反馈的优先处理

若收到隐私质疑，**24 小时内**完成核实与回复，不得搁置。

核实步骤：

1. 确认反馈指向的具体行为
2. 对照 `COMPLIANCE-AUDIT.md` 查证实际代码行为
3. 若反馈属实且与文档不符 → 属 P1 文档缺陷，需修订文档
4. 若反馈不属实 → 用事实回复，说明对应代码位置
5. 若发现文档与行为都不符 → 升级为 P0

**回复模板要点**：承认问题、给出事实、说明已采取的措施。不用「我们不会收集任何数据」这类绝对表述来回避具体疑问。

---

## 5. V0.3 候选清单的建立

所有不实施于 V0.2 的反馈汇入 V0.3 候选清单，按下列维度排序：

| 维度 | 说明 |
|---|---|
| 用户影响 | 有多少用户提出、影响多严重 |
| 与产品定位的契合度 | 是否强化「可解释 + 最小权限 + 用户确认」 |
| 实现成本与风险 | 是否触及安全边界、是否需要新权限 |
| 前置依赖 | 是否依赖尚未具备的设备矩阵或性能基线 |

清单同时记录**明确拒绝**的项及其理由，避免后续反复讨论同一问题。

---

## 6. R7 产出物

评审结束后必须产出：

| 产出物 | 内容 |
|---|---|
| 反馈处理结论表 | 每条反馈的处理决定与理由 |
| P0/P1 清单 | 转入 R8 的问题，含复现步骤与根因 |
| V0.3 候选清单 | 排序后的功能候选，含明确拒绝项及理由 |
| 文档修订清单 | 因反馈而需要修订的合规或说明文档 |
| 政策质疑回复归档 | 隐私与合规类反馈的完整回复记录 |

---

## 7. 退出条件

- [ ] 全部反馈已归档并有处理结论
- [ ] P0/P1 清单完整，每项有复现步骤与根因分析
- [ ] V0.3 候选清单已排序，含明确拒绝项及理由
- [ ] 政策质疑全部回复完毕
- [ ] 文档修订清单已执行
- [ ] 项目所有者书面确认进入 R8

---

## 8. 与 R8 / R10 的关系

- **R8** 只修复 release-blocking 缺陷。每次修复必须有：复现步骤、根因证据、回归测试、相关 OEM 验证（如涉及）、以及新的不可变 RC tag。
- **R10** 决定 V0.3 是否立项。R7 产出的 V0.3 候选清单是 R10 评估的主要输入。

**R7 不会产生新功能。** V0.2 的功能范围在 R0 冻结时已确定，R7 只处理「已发布的功能是否按设计工作」。
