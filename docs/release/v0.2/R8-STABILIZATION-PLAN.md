# CleanGuard V0.2 R8 发布阻塞缺陷稳定化方案

**状态**：方案就绪，待 R7 评审结论产出后执行
**前置条件**：R7 评审完成，「阻塞项」与「功能缺陷」两栏已确定
**目标**：把 R7 判定的必修缺陷修完并证明没有引入新问题

---

## 1. 范围

R8 只处理 R7 评审结论中判为**阻塞发布**与**功能缺陷**的两类。

不在范围内：

| 项 | 归属 |
|---|---|
| 功能请求 | V0.3 候选 |
| 文案与引导改进 | R7 误解项，直接改，不进 R8 排期 |
| 其他 ROM 的兼容问题 | R2 设备矩阵 |
| 结构性重构 | V0.3 |

**边界必须清楚**：R8 是稳定化，不是新功能开发。混进新功能会让发布日期失去意义。

---

## 2. 严重度与处理时限

沿用 `BUG-TRACKER.md` 的严重度定义：

| 级别 | 定义 | 处理 |
|---|---|---|
| P0 | 数据丢失、错误删除、崩溃循环、DANGER/UNKNOWN 被删、权限绕过、数据库损坏 | 立即修复，优先于一切 |
| P1 | 扫描失败、回收站/恢复失败、严重 ANR、主界面不可用 | 本轮必修 |
| P2 | 可复现的 OEM 兼容问题、明显性能回退、重大界面错误 | 本轮必修（若可复现且影响面可控） |
| P3 | 轻微界面、文案、非核心体验问题 | 不进 R8，记录到 V0.3 |

**P0 与 P1 必须清零才能进入 R9。** P2 若因复现条件受限无法在本轮完成，需在 R9 决策中显式记录并由项目所有者接受风险。

---

## 3. 修复原则

### 3.1 行为修复优先于文案修复

如果一条反馈可以用改文案解决，但根因是行为与承诺不符，**改行为**。
CleanGuard 的安全承诺是硬约束：

- DANGER / UNKNOWN 不得进入清理计划
- REVIEW 默认不选中
- 只对合格的 MediaStore 项目请求系统回收站确认；SAF 文件只预览/分享/定位
- 移入回收站通常不立即释放物理空间，不得伪造已释放空间
- 重复文件只是 REVIEW 建议，不自动决定保留哪个

**任何为了「让反馈消失」而放宽以上约束的改动都不允许合入。**

### 3.2 每个修复都要有回归证据

修复完成后必须记录：复现步骤、修改点、验证方式、回归结果。
没有回归证据的修复视为未完成。

### 3.3 不在 R8 引入新权限

R8 期间**不得新增任何运行时权限**，也不得修改现有权限的申请时机或范围。
若某缺陷的唯一修法是新增权限，该缺陷进 V0.3，R8 用绕行方案或文案说明处理。

## 4. 执行流程

### 4.1 建立缺陷清单

以 R7 的评审结论为输入，在 `BUG-TRACKER.md` 的「Active bugs」表登记：

| 字段 | 要求 |
|---|---|
| ID | `V02-BUG-<序号>` |
| Severity | P0 / P1 / P2 |
| Environment | 设备型号、系统版本、ROM、是否可复现 |
| Reproduction | 逐步可复现，不写「偶现」而不给条件 |
| Expected / actual | 期望与实际分开写 |
| Owner | 负责人 |
| Status | 待修 / 修复中 / 待验证 / 已验证 |
| Regression evidence | 验证完成后填写 |

### 4.2 逐条修复

每条缺陷走同一条路径：

1. 先写一个能复现该缺陷的自动化测试（或在 `tools/manual-tests/` 里加一个场景）
2. 确认测试在修复前**失败**
3. 修改代码
4. 确认测试在修复后**通过**
5. 跑完整套件，确认没有连带破坏

**第 2 步不可跳过。** 没有「修复前会失败」的测试，无法证明测试真的覆盖了这个缺陷。

### 4.3 完整回归

修复全部完成后，跑一次完整验证：

```bash
# 单元测试
./gradlew.bat :app:testDebugUnitTest :app:testReleaseUnitTest

# 设备端自动化
./gradlew.bat :app:connectedDebugAndroidTest

# 手工场景
python3 tools/manual-tests/run-scenarios.py <serial>
```

设备端与手工场景需要真实设备。R2 设备矩阵上的每台设备都要跑一遍完整套件，
而不只是跑过修复的那条。
